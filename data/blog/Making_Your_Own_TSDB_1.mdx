1. LSM Tree

There majority of databases uses B/B+ Tree or LSM-Tree or their variations as their core data structure to store data depending on the use case, LSM-Tree in particular is used to store data in a way which is generally optimized for write heavy workloads.
Unlike B/B+ Tree, LSM-Tree is not actually a tree but rather a multi component data structure where LSM stands for 'Log Structured Merge', each of these 3 keywords define the 3 core properties of it which are:

 1 Log: LSM-Trees are mostly designed with appennd-only logic, meaning any mutable action on the database creates a new entry instead of modifying the existing one in-place, for example deletes and updates do not modify the existing data but rather create a new entry
 
 2 Structured: The data is stored in a strictly organized and structured way, it is first stored in primary memory inside a sorted dictionary data structure and then flushed to the disk in the samen manner, so that during reads t he system could use binary search or indexes to quickly locate the data instead of scanning whole database.

 3 Merge: Because data is written as an append-only log, the system will inevitably end up with multiple versions of the same data spread across different disk files (Ex- an insert in file 1, an update in file 2, and a delete in file 3). To fix this, a background process called compaction takes these separate sorted files and combines them using a merge sort algorithm.

2. Why LSM-Tree 

Time series databases are primarily used for analyzing and ingesting large volumes of timestamped data at an extremely high rate without choking, some usecases include, storing ticker data for a stock from the financial market, or ingesting telemetry data for observability. In many use case the rate at which this data is produced is extremely fast and LSM-Tree is a widely recognized data structure for this specific use case.

many modern analytical databases often uses a variation of LSM-Tree based storage engines, to handle high rates of ingestion, some example include: 

 1. ScylllaDB: Uses a shard-per-core architecture combined with a Log-Structured Merge-tree to maximize performance.
 2. VictoriaMetrics: A high performance time series data base useed for monitoring internally it relies on Merge-Tree based storage engine which is a variation of LSM-Tree.
 3. ClickHouse: A fast analytical database which uses Merge-Tree internally as a part of it's storage engine.
 4. RocksDB: Key value store developed by meta for write heavy scenarios.

### 1. Memtable

In my opinion memtable is unarguablly the most important part of a LSM-Tree, one can think of it as the in-memory, dictionary data structure(key-value) which maintains incoming data in a sorted way, they are kept small in size, usually in order of mega bytes.

This is where every write/delete/update request lands and appends a new entry to, one of the major responsibility of this data structure is to store the incoming entries in a sorted manner and eventually when the memtable is full we flush this memtable into the secondary memory as a SST.

it is the also the starting point for read queries, if the data is not found in the memtable, only then it moves forward to locate it in the rest of the database, and this gives us a scope of optimization on the read path, what if we can quickly and correctly predict if a key does "NOT" exist in the memtable, if you also thought about using a bloom filter then you are rigt, if you don't know what a bloom filter is you can read about it [here](https://chahatsagar.substack.com/p/i-wanted-to-understand-bloom-filters) , we can maintain a bloom filter for our memtable and before and before searching the memtable we would use the bloom filter to check "if the data certainly doesn't exist or not", if the is exist, means the result could be a false positive and now we would check for the data inside the memtable.

Based on these properties there are multiple data structures that could be used as a memtable such as B/B+ Tre, Red-Black Tree, Skip-List or an AVL-Tree. I was particularly more oriented towards building a concurrent version of a lockfree Skip-List to be used as memtable in my database.


### 2. SSTable 

This one stands for "Sorted String Table", in simple terms one can think of SSTs as immutable chunks of data that is persisted in secondary memory i.e when a memtable reaches it's capacity the sorted data inside it is flushed into the secondary memory too be persisted in form of a sorted string table.

SSTs can have multiple sub-components inside them. In most implementations you’ll find the following parts:

<LSM_SST />
#### Sparse Index Table
A small index that stores the file offset of every N‑th key, used to speed up reads. When a lookup is performed, the engine first reads the sparse index, determines the nearest offset, and then scans only that short slice of the data table.

#### Data Table 
It is the sequence of complete data that was flushed from the memtable. Since this data is sorted in terms of key, a simple binary search can be used to locate a key in O(log N) time.

#### Bloom filter
These are SSTable level bloom filters that records which keys are present in it, again used to speed up search as it can correctly predict if a particular entry "does not" exist in the SSTable without actually traversing over the keys.

#### Meta Data 
A small footer that contains global information about the SSTable, such as:
 Total file size
 Minimum and maximum key stored
 Offsets to the sparse index, data block, and bloom filter
 Compression scheme, checksum, etc.

When a Memtable fills up, its sorted entries are flushed to disk as a new SSTable.
If we kept doing this without any further organization we would quickly end up with thousands of SSTables, which makes reads expensive because the engine would have to probe many files.

To avoid this, LSM‑based storage groups SSTables into levels as shown below, level 0 contains freshly flushed SSTables, after a certain threshold compaction occours and a level 1 SSTable is created from several level 0 SSTables, similarly aafter a certain threshold level 1 SSTables are compacted into a level 2 SSTable and so on, we will take a batter look at compaction and it's details in later section.

### 3. Write Ahead Log

This is a log file in the secondary memory which we use for crash recovery, basically whenever we do a mutable operation like Write/Update/Delete on the data base, we maintain a record of it so that if the database dies before flush we should be able to recover/rebuild the memtable. 

But if we are we going to fsync each operation to WAL before applying it on the memtable isn't it going to affect write throughput ? and the answer is yes. but if a crash ever happens and the memtable was not flushed, we can guaruntee recoverability upto the last succesfull operation so data recoverability/safety here is maximum.

This is a tradeoff between performance and data safety guaruntee which could be understood form the below table: 

| Strategy | How it works | Write‑performance impact | Data‑safety guarantee |
|----------|--------------|--------------------------|------------------------|
| **Synchronous WAL** | fsync after each log entry | A disk sync on every operation | Durability up to **last successful write** |
| **No WAL** | Modify the Memtable directly | Very fast, no extra I/O | If a crash occurs, the entire Memtable is lost |
| **Batched WAL** | Append entries to the OS page‑cache, then flush them in batches (e.g., every 1 s or every N operations) | minimal most of the time; occasional sync when the batch is flushed | Guarantees durability up to the **batch window** (e.g., 1 s or N ops) |

The choice for batch window depends on use case and may vary across databases. For examplle InfluxDB calls fsync on every write, Cassandra keeps it at 10 second, whille VictoriaMetrics does not use WAL at all, however for my specific case, I am plannign on keepign WAL with a batched flushing setup to ensure both recoverability and performance.

## 4. Compaction Scheme  

Compaction is a process which runs whenever a level of SSTables becomes full. Its purpose is to merge several SSTables into fewer, larger ones using a merge‑sort‑like algorithm so that:

* Redundant entries created by the append‑only write path (updates → new rows, deletes → tombstones) are eliminated.  
* Disk space in the current level is reclaimed.

Below I have attatched a visualization that shows why append only design results in data redundancy and how compaction is used to address this issue.

<LSM_Compaction />


**Key steps**

1. **Flush** - When the Memtable fills, its sorted data becomes one or more Level‑0 SSTables.  
2. **Trigger** - Once a Level reaches a size/count limit, compaction starts.  
3. **Merge** - Overlapping SSTables are read in key order, for each key only the latest value is kept.  
4. **Write‑out** - The merged result is stored as new SSTable(s) in the next level (L1, L2 …).  
5. **Clean‑up** - Old SSTables are deleted, reclaiming space.

There exists multiple strategies for compaction depending on desired outcomes and use case, however there are 2 main widely adapted strategies for compaction which are: 

1. **Leveled compaction** - Guarantees non‑overlapping SSTables in each level while also cleaning up redundant entries. This usually causes higher write amplification, but it keeps reads fast. I personally find it more interesting and  am going to use it in my database implementation.

2. **Size Tiered compaction** - Keeps the compaction step simple and low‑cost by merging multiple SSTables together into one big SSTable, here key ranges can overlap, so a read may have to check more SSTables to find the latest value, resulting in higher read amplification.

These two descriptions are only introductory. A full article is required to cover the details of each strategy, their tuning knobs, and their impact on performance. I’ll leave the deeper discussion for later.

## 4. Write Path

Writes in an LSM-Tree is a multi step process that roughly follows the following path: 

1. Write query comes in. 
2. The query is logged in OS cache
3. Operation is applied on Memtable and bloom filter
4. When the OS page cache reaches it's capacity, logs are flushes into the WAL file
5. When the memtable reaches it's capacity, it is flushed along with the bloomfilter to create a new SS table in level 0
6. When a particular level reaches it's threshold for the number of sstables allowed, it undergoes compaction.

## 5. Read Path

Reads in LSM-Trees are actually quite straightforward once you understand one simple fact "LSM-Trees are append-only". What this means for reads is that the latest version of any data always lives at the top of the hierarchy. The Memtable holds the most recent writes, Level-0 SSTables hold slightly older data, and as you go deeper into the levels the data gets progressively older. So when we're looking for a key, we start at the top and work our way down, the first match we find is guaranteed to be the latest version, and we stop right there.

The read order is:  
1. Step 1 : Read in memtable
2. Step 2 : Set level L as 0
3. Step 3 : If not found seach the level L SSTables in newest to oldest SSTables
4. Step 4 : If not found increment L and go to Step 2.
5. Step 5 : If the data is located or L goesgreater than threshold of levels, stop.


The reason we search within each level in newest-to-oldest order is the same — since SSTables within a level were created at different points in time, the newer ones may contain more recent updates for the same key.


### Searching the Memtable

We first run the key through the Bloom filter to check if the key certainly does not exist there. If the Bloom filter says no, we skip the Memtable entirely. Only if it says "probably yes" do we actually search inside it.

This is a small but powerful trick for queries where the data simply doesn't exist in the Memtable we avoid a lookup entirely and move on faster.

### Searching an SSTable

If the key wasn't found in the Memtable, we move on to the SSTables. The main challenge here is keeping I/O as low as possible, we really don't want to load an entire SSTable into memory just to check if a key is in it.

Here's the approach:

1. Read the footer (Meta Data) - The footer contains byte offsets of the Bloom filter and Sparse Index Table inside the file. We load only these two.
2. Check the Bloom filter - Run the key through the SSTable's Bloom filter. If the key certainly doesn't exist, we skip this SSTable.
3. Use the Sparse Index to narrow the range - If the key probably exists, we look up the nearest indexed key in the Sparse Index Table to get an approximate byte offset in the data table.
4. Load only that memory page - Using that offset, we fetch just the specific page of the data table where the key should live. This way we only pull the most necessary slice of data from disk into memory, keeping I/O minimal.
5. Scan the page - Since data within an SSTable is sorted, we do a quick scan or binary search over that small page to find our key.

If the key isn't found in this SSTable, we move on to the next one in the same level, and then to the next level if needed. If we exhaust all levels without a match, we return "not found."
